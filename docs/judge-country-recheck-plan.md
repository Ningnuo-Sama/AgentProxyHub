# 判国探测重修方案（事件驱动替代定时轮询）

> 起因：2026-10-15 流量治理时，用户要求先关停账号判国探测，保留以后自己重修。
> 本文记录**为什么必须关**、**重修时该走哪条路**，以及**不能再走的老路的具体形态**。
>
> 结论先说：不要恢复「定时全量判国」。改为**事件驱动 + 按需单点判国**。

## 1. 为什么必须关（实测数据）

治理前的流量画像（2026-10-15 凌晨实测）：

| 探测源 | 频率 | 覆盖 | 单日流量贡献 |
| :--- | :--- | :--- | :--- |
| AUTO-POOL url-test | 180 秒 × 124 节点 | 全部端口池 | 主要来源 |
| account-guard 判国 | 300 秒 × 13 端口 | 仅已绑定端口 | 次要来源 |
| 两者叠加 | — | — | **约 17 GB/天** |

`bridge.log` 今日 631 行中，**571 行**是 `policies.google.com` 的判国探测请求。失败后 mihomo 对死节点不降频、照探不误，形成绞肉机：

```
fw-21003 -> 121.14.13.199:48413  连接被强制关闭   ← 121.14.13.199 是中国电信落地
fw-21004 -> 121.14.13.199:7204   i/o timeout
xc-22001 -> 18.167.36.222:15466  主动拒绝
```

计费细节：判国探测走的是真实 TLS 握手，`policies.google.com/terms` 页面按 HTML 计下载，单次约 3–8 KB。124 节点 × 480 轮/天，即使 90% 失败也有可观的上行握手流量。

**代价与收益严重不对称**：换来的只是「周期性知道出口漂没漂」，而实际业务请求本身就会在漂移时立刻报错。

## 2. 它原本确实有用（保留这个认知）

2026-10-13 那次 Flow-Tools 号池事故，就是 account-guard 发现的：21013/21007 出口 Ukraine、22003/22008 出口 Macao，而 bindings.json 承诺 US，触发 Google 400「地区不支持」。

所以重修目标不是「不要告警」，而是**用便宜的方式得到同样的告警**。

## 3. 重修方向：事件驱动

### 核心思路

把判国从「主动轮询」改为「**被动触发**」。三类触发器：

| 触发器 | 检测方式 | 判国动作 | 成本 |
| :--- | :--- | :--- | :--- |
| 业务请求失败 | 上游返回 400 / 403 / 「地区不支持」 | 只对**该账号绑定的那一个端口**判国 | 极低（失败时才花） |
| 出口 IP 变化 | mihomo `/connections` 或 `/proxies` 的出口 IP 与基线不同 | 只对该端口判国确认 | 低 |
| 显式体检 | 用户手动跑 `account_guard.py` 不带 `--fix` | 全量 | 可控，按需 |

### 落地要点

1. **触发器一（最重要）**：现有 `account_guard.py` 已经有 `at_config()` 读 Antigravity 8045 网关的能力。改为监听其健康状态/错误码，而不是定时探。业务本来就在发请求，**失败即信号**，此时判国是「已经出事了才花流量」，而不是「没出事也天天花」。
2. **触发器二**：`/connections` 的 `metadata.destinationIP` 或 `/proxies` 的出口 IP 与 `bindings.json` 里记录的基线 IP 比对。IP 变化不等于漂移（Google 可能改判同 IP 国别，10-13 事故正是如此），所以 IP 变化只作为**疑似信号**，仍需一次判国确认——但这已经比定时轮询省了几个数量级。
3. **单一端口判国函数**：保留 `core/net_probe.py` 的 `probe_google_country_direct(port, timeout)`。它只对一个端口发一次请求，是判国的最小单元，重修时直接复用，不要重写。
4. **告警去重逻辑必须保留**：现有 `cur_bad != prev_bad` 才 `notify_all()` 的写法是对的，异常集合不变则跳过告警。重修时别丢掉，否则每次触发都推送微信会立刻被用户骂。

### 明确不要做的事

- ❌ 不要恢复 300 秒定时全量判国
- ❌ 不要恢复 `auto_rebind_enabled=true` 的自动换绑（用户明示不需要，且自动换绑会引入 IP 跳变，反而触发风控）
- ❌ 不要把判国塞进 `AUTO-POOL` 的 url-test（那是测延迟用的，语义不同，混在一起只会两个都做不好）
- ❌ 不要在探测失败时提高重试频率（10-13 事故里 `repair_events.jsonl` 曾自愈到 Ukraine 并放行，漂移是自愈自己造成的）

## 4. 与 AUTO-POOL 的关系

本条常被混淆，单独说明：

| | AUTO-POOL url-test | 判国探测 |
| :--- | :--- | :--- |
| 目的 | 选延迟最低的出口 | 确认出口国家是 US |
| 判据 | `gstatic.com/generate_204` 响应时间 | `policies.google.com` 返回的国家名 |
| 治理后状态 | 4 节点 / 1800 秒（`gen-config.ps1 -AutoPoolProbeNodes` 白名单） | 已停用 |

两者**互不替代**：url-test 选出的最低延迟节点完全可能是香港（125–140ms 最快），而 Google 判国对香港一律不支持。所以不能「AUTO-POOL 选出来的就是合规的」。

治理后的权衡是：**只让 4 个已验证的「AI 直连」节点参与自动优选**，其余 123 个仍可作为人工可选（ALL 组）但不自动探。人工选节点时自己知道选了哪里。

## 5. 重修验收标准

做完后按这四条验，缺一条不算完：

1. 空闲状态下 `/connections` 连接数为 0、`bridge.log` 60 秒增量为 0 字节
2. 构造一次业务失败（如临时把某端口出口换到受限区），判国告警能在**单端口**触发，且只触发一次
3. 告警不重复推送（`account_guard_state.json` 的 `problems` 集合不变则不推）
4. `paid_calls=false`、`bindings_changed=false`（不自动换绑、不产生付费调用）
