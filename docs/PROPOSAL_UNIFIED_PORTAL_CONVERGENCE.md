# 【技术架构提案】出海多环境与自动化生态工作台收敛方案（NERV Unified Portal）

## 一、 现状痛点与重构动因

目前本地出海矩阵生态中并存三个核心项目：
1. **AgentProxyHub**（`D:\GitHub\AgentProxyHub`）：基于 mihomo 的出海专线中枢、节点健康审计、DPAPI 凭据金库与 MCP 服务。
2. **CloakMulti**（`D:\GitHub\CloakMulti`）：基于 CloakBrowser（Chromium 146）的指纹多开、Cookie 加密冷备、Google 账号与 2FA 管家。
3. **Flow-Tools**（`D:\GitHub\Flow-Tools`）：基于 Tauri/Rust 的 Google Labs 会话换票、打码调度、短命 Token 刷新与生图/视频 API 网关。

### 当前痛点：
- **碎片化严重**：三个软件各自起独立的系统托盘、各自占用分散端口（7800、20090、21001+ 等）、各自弹窗口，桌面极度臃肿。
- **孤岛感强**：`AgentProxyHub` 作为纯网络中枢，没有直接的业务承载界面，单独使用场景显得单薄；而 `CloakMulti` 和 `Flow-Tools` 虽依赖出口池，却需跨进程、跨文件对账。
- **运维成本高**：用户需要分别启动、分别保活，任何一个进程因休眠或异常退出都会导致上下游断链报错（如前端 `Failed to fetch`）。

## 二、 历史审查释疑：为什么之前反对“合并”，而今天主张“收敛”？

在 2026-09-29 的架构决策中，曾有明确结论：*“坚决不把打码和生图业务塞进 AgentProxyHub，基础设施必须纯粹轻量。”*

必须澄清：**本提案的“工作台收敛”与此前反对的“代码大乱炖（Monolith）”有本质区别：**

| 架构维度 | 2026-09-29 坚决反对的“合并” | 本提案主张的“生态收敛” |
| :--- | :--- | :--- |
| **代码组织** | **源码混为一谈**：把打码、Playwright、Rust 网关硬塞进 AgentProxyHub 仓库 | **物理严格解耦**：保持 3 个独立的 Git 仓库，各自独立拉取上游 |
| **故障域 (Blast Radius)**| **雪崩同死**：打码超时或浏览器 OOM 会直接拖垮总代理内核，全机断网 | **进程硬隔离**：子模块为独立子进程/反代服务，崩溃时不波及网络中枢 |
| **上游同步能力** | **完全丧失**：混合仓库无法直接追踪 `flow2api` 或 `CloakBrowser` 上游更新 | **完全保留**：子项目在各自目录下执行原生 `git fetch / pull`，零冲突 |
| **收敛形态** | 代码级强耦合（Monolithic Mud） | **前台聚合工作台 + 本地反代网关（Federated Portal）** |

## 三、 整体系统拓扑：微内核与插件式门户（Hub-and-Spoke）

采用 **“单一桌面宿主（Host）+ 本地反向代理（Reverse Proxy Gateway）+ 独立模块热挂载（Decoupled Engines）”** 架构：

```text
┌─────────────────────────────────────────────────────────────────────────────┐
│                 NERV Central Tactical Dock (统一桌面工作台)                   │
│  [ 🛰 出口网络池 ]  │  [ 🌐 指纹环境/账号 (Cloak) ]  │  [ ⚡ 自动化任务 (Flow) ]  │
└──────────────────────────────────────┬──────────────────────────────────────┘
                                       │ 统一加载主界面 / 单一系统托盘
                                       ▼
┌─────────────────────────────────────────────────────────────────────────────┐
│                AgentProxyHub 统一守护宿主 (127.0.0.1:21000)                   │
│  - 主桌面外壳 (WebView2/Tauri 统一宿主)                                       │
│  - 本地反代网关 (Reverse Proxy: /api/proxy/*, /api/cloak/*, /api/flow/*)      │
│  - 单一真理账本 (Single Source of Truth: data/bindings.json)                │
│  - 全局进程看门狗 (Supervisord-like Process Watchdog)                         │
└──────────────┬───────────────────────┬──────────────────────────────┬───────┘
               │                       │ (反代/本地HTTP)              │ (反代/本地HTTP)
               ▼                       ▼                              ▼
    ┌──────────────────────┐ ┌──────────────────────┐  ┌──────────────────────┐
    │  Network Engine      │ │  Profile Engine      │  │  Automation Engine   │
    │  (AgentProxyHub 核心)│ │  (CloakMulti 模块)   │  │  (Flow-Tools 模块)   │
    ├──────────────────────┤ ├──────────────────────┤  ├──────────────────────┤
    │ · mihomo 专线内核    │ │ · Chromium 146 多开  │  │ · 会话换票 & 校验    │
    │ · 21001+ SOCKS5 出口 │ │ · Google 账号/2FA    │  │ · reCAPTCHA v3 打码   │
    │ · DPAPI 凭据金库     │ │ · 加密备份 & Cookie  │  │ · Veo/Imagen 生成网关│
    │ · MCP Server 调度    │ │ · 独立端口 7800 (内网)│  │ · 独立端口 20090(内网)│
    └──────────────────────┘ └──────────────────────┘  └──────────────────────┘
               ▲                       ▲                              ▲
               │                       │                              │
         [各机场/专线上游]        [CloakBrowser 上游]          [flow2api 双上游]
```

### 核心分工说明：
1. **L1 基建层（AgentProxyHub Core）**：
   - 守住纯粹性：只管专线打通、21001-21080 端口映射、IP 粘性锁、DPAPI 凭据安全与 MCP 工具集。
2. **L2 资产层（CloakMulti Module）**：
   - 只管身份：环境参数、指纹多开、Cookie 安全导入导出、2FA 自动计算。
3. **L3 任务层（Flow-Tools Module）**：
   - 只管业务：调用 L2 提供的免密登录环境提取 Session Token，通过 L1 提供的专属代理端口与 Google 交互，执行媒体生成。

## 四、 如何实现“模块独立、随时拉取单独上游”？

这是本方案设计的精髓所在，通过 **「工程物理隔离 + 运行时本地服务发现」** 实现：

### 1. 物理目录结构（完全不破坏 Git 边界）
```text
D:\GitHub\
├── AgentProxyHub\        (主仓库：负责主界面框架、代理中枢、反代网关、MCP)
├── CloakMulti\           (独立仓库：负责指纹浏览器环境与账号资产)
└── Flow-Tools\           (独立仓库：负责 Google Labs 会话换票与打码生成)
```
- 每个目录都有自己独立的 `.git`、分支和 upstream remote；
- 当 `TheSmallHanCat/flow2api` 或 `CloakBrowser` 发布新补丁时，开发者直接在对应目录 `git fetch && git merge upstream/main`，**与主工作台代码零物理交叉，绝无代码冲突**。

### 2. 本地服务发现与反向代理（Reverse Proxy Auto-Mount）
- `AgentProxyHub` 启动时，自动扫描同级目录是否存在 `..\CloakMulti` 和 `..\Flow-Tools`：
  - 若检测到 `CloakMulti`：在后台以子进程拉起其轻量服务（监听仅供内网回环的隐藏端口），并在前端主导航点亮 **【指纹环境】** 标签页，所有路由 `/cloak/*` 反代转发至该子服务；
  - 若检测到 `Flow-Tools`：拉起其网关服务，在主导航点亮 **【自动化生成】** 标签页，路由 `/flow/*` 反代转发；
  - 若某个子模块未安装或被用户移除：主工作台**平滑降级**，仅隐藏对应标签页，底层代理中枢与金库功能丝毫不受影响。

### 3. 数据与账本协议（零拷贝与单一真理源）
- **代理出口账本**：唯一真理源锁定在 `AgentProxyHub/data/bindings.json`。CloakMulti 与 Flow-Tools 严禁私建代理记录，统一以此文件为准。
- **环境资料与 Cookie**：采用已验证成熟的 **NTFS 目录联接（Junction / Zero-Copy）**，Flow-Tools 通过无损热迁移标准直接联接 CloakMulti 的环境资料，不产生数据重复冗余。

## 五、 实施路线图（三步平滑演进）

### 第一阶段：网关反代与主界面聚合（Portal MVP）
- 保持 CloakMulti 和 Flow-Tools 原有代码完全不动；
- 在 `AgentProxyHub` 中建立一个统一的聚合 Web 控制台（EVA 风格侧边栏）：
  - 侧边栏菜单：`[ 🛰 专线中枢 ]`、`[ 🌐 环境多开 ]`、`[ ⚡ 任务工作台 ]`、`[ 🔑 凭据金库 ]`；
  - 通过 iframe / WebComponents + 反向代理，将分散的页面聚合进同一个主窗口。
- 收益：**桌面立刻只剩一个总窗口，端口统一由网关收敛。**

### 第二阶段：桌面托盘与看门狗统一（Unified Host）
- 由 `AgentProxyHub` 作为系统开机自启的**唯一桌面外壳（Desktop Host）**；
- 宿主内置 Supervisord 级子进程守护：
  - 统一管理 AgentProxyHub 内核、CloakMulti 后台与 Flow-Tools 网关的拉起、退出与崩溃自愈；
  - 清理电脑右下角冗余托盘图标，只保留一个“NERV 中枢”托盘。
- 收益：**彻底解决孤儿进程与主外壳还在但后台已死的死锁问题。**

### 第三阶段：深层业务能力自动化联动
- 在统一工作台内打通流水线动作：
  - “选定高分美区出口 → 一键在 Cloak 中派生环境并锁定粘性 → 自动移交 Flow 换票入库”的一站式流转。

## 六、 针对架构评审的预设答辩（FAQ）

- **Q1: 模块都在一个工作台里，某个模块挂了会拖垮整个网络吗？**  
  **A**: 绝对不会。三者在操作系统级是**独立的子进程**。Flow-Tools 的打码或生图崩溃，仅仅是该子进程退出；主宿主会捕获该事件并尝试自愈，底层的 mihomo 专线内核与出口网络完全不受影响。
- **Q2: 上游 API 协议频繁变动，真的能做到无感更新吗？**  
  **A**: 必须能。因为物理仓库是完全隔离的。Flow-Tools 的开发人员可以随意使用 Cargo/Vite 在自己的仓库内重构、拉取 `TheSmallHanCat` 上游代码并单独测试，只要其暴露给反代网关的 REST/HTTP 契约保持稳定，主工作台无需改动一行代码。
- **Q3: 为什么这比现状好？**  
  **A**: 现状是“九龙治水”，三个软件互相猜对方在干嘛，用户要开三个面板，出错了不知道哪个进程掉了。收敛后是“联邦制”，前台统一收口于大厅，后台各司其职，用户心智负担降至最低。
