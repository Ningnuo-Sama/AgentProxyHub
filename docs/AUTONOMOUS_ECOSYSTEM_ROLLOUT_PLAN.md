# 出海账号与代理生态自动化落地计划书

> 版本：2026-09-30 v1.0
> 状态：落地计划，尚未代表已部署或已完成验收
> 策略优先级：以下“效率优先执行版”覆盖本文后续旧版的串行阶段、默认观察期和逐次人工审批建议；后续细节仍需按此执行版统一修订。微信通道按用户已打通的现有资产复用，不重建。当前请求是修订计划，不代表本轮启动部署或运行认证。 

## 效率优先执行版

### A. 交付方式

不新建大型 Orchestrator 产品、不新增仪表盘、不增加第七个常驻管理平台。先在 AgentProxyHub 现有服务能力上扩展轻量 AutoPilot，使用现有项目适配器和持久化任务队列。网络动作由 Hub 执行、认证与账号动作由所属网关执行；GLM 只提供建议，确定性规则负责授权与执行检查。

### B. 并行三条实施线

1. **网络自愈线**：统一账本路径和并发锁 → 订阅增量更新 → 保留端口映射 → 故障节点隔离 → 同国候选切换 → 成功回读/失败回退。只有故障触发切换，不为跑分或线路恢复主动来回迁移账号。
2. **登录纳管线**：Cloak 登录完成事件 → Flow 热导入接口（待实现，非已有事实）→ 主体/会话验证 → 激活。先自动编排已有 sync-profile 作为兼容路径，在线提取成熟后替换；不得随意关闭用户正在操作的浏览器。Antigravity 使用自有 OAuth 授权与导入适配器；一处 Google 登录不保证自动获得所有服务授权，有真实新增授权要求时才邀请用户处理。
3. **恢复与通知线**：统一错误分类 → 冷却/续期/已有授权2FA → 接入现有微信发送器 → 去重和升级。普通局部故障修好后静默；单号坏而其余池仍可工作时先隔离，不阻断整池。

三条线各自在候选环境验证；完成账本、鉴权、状态恢复这三个前置条件后立即进行单号真实闭环，不以固定24–72小时等待期阻塞发布。较长观察在部署后后台持续完成。

### C. 自动处置授权矩阵

- 既有权限内的同国节点切换、跨服务商同国切换、配置恢复、账号冷却、缓存重载、受支持凭据续期：策略检查通过后自动执行，不逐次问用户。
- 合法服务覆盖区域内跨区恢复：仅对已配置允许区域的账号执行；无候选时先切换另一个可用账号，不为单号失效打扰用户。
- 明确地域限制、账号禁用或平台强制人工验证：不把换线或认证辅助当作规避方式。
- 2FA：仅本人管理账号、已授权验证器和真实认证挑战；不收集陌生账号验证码。
- CAPTCHA：记录本地能力授权，待正式技术契约核验官方无障碍/服务认可方式后接入；当前不调用、不假定已可用。
- 数据损坏、凭据泄漏、所有业务能力持续不可用、必须用户完成授权：立即升级重要事件。

### D. 通知条件以业务影响为准

不因每一个节点故障、一个账号过期、一次切换或一次自动恢复发微信。恢复尚未成功但存在可用替代账号时，仅进本地待办。系统应判断：是否仍能交付用户任务、是否有不可逆风险、是否必须用户操作。只在这三种条件确实需要人时通知。

初始重要告警规则：全部业务池不可用并持续5分钟；已检测凭据泄漏或数据写入损坏立即通知；必要人工认证无法替代时通知。短暂恢复成功不再发送恢复消息；重要告警已发送的事件，恢复后只发一次结案信息。阈值是初始建议，不是已实测承诺。

### E. 不让模型成为恢复单点

规则直接处理可识别故障；GLM只处理原因归纳和复杂候选排序，不让每次HTTP失败都调用模型。GLM失活时仍可通过确定性策略执行同国恢复。模型输出严格校验，不能生成任意shell并自动执行。

### F. 实现必补的效率护栏

- 确认媒体任务未成功提交后才重试；提交结果未知先查询任务状态，防重复扣点。
- 暂停新任务、等待在途任务或有界取消后再换出口；新出口失败只回退一次，不制造来回震荡。
- 状态落盘、崩溃重启接续、幂等导入、防双消费必须在首版实现。
- 告警路径尽量与被监控的LLM网关解耦；既有微信桥失活时事件本地持久化待补发，不能声称消息已送达。
- 代理订阅刷新按provider独立判断故障，避免一条机场线路劣化触发全池重建。

### G. 首版完成标准

用户只登录并完成服务必要授权；之后系统自动入池、网络维护、续期和恢复。至少验证单节点失效、provider失效、账号过期、重复导入、服务重启、任务提交未知以及微信去重；普通故障零人工介入，重要事件有明确处置消息。首版不追求全模型智能路由和新UI，先交付端到端可运行闭环。
> 适用项目：AgentProxyHub、CloakMulti、Flow-Tools、Antigravity-Manager、GLM-4flash、手机分身
> 核心诉求：用户完成账号登录后，系统自动完成网络维护、状态同步、健康调度和普通故障处置；只有真正需要人决策的事件才通过微信通知用户。

## 1. 用户授权与产品目标

用户明确接受自动换线、自动隔离、自动认证辅助和自动恢复的风险，以换取最大化提效。系统目标不是“遇到风险就停”，而是：

- **默认无人值守**：账号登录完成后，系统自行完成纳管、维护、调度和恢复。
- **自动优先**：节点巡检、订阅刷新、代理重载、同区切换、跨服务商切换、账号冷却、认证辅助、有限跨区恢复和任务重试均由系统优先处理。
- **失败才升级**：只有自动化预算耗尽、认证主体不一致、连续验证失败、数据损坏或整个基础设施失活才暂停并通知。
- **微信只报要紧事**：日常成功、普通重试、网络切换、订阅更新、账号冷却和认证辅助成功全部静默；微信是异常处理台，不是日志窗口。
- **认证自动化已获用户授权**：CAPTCHA 使用 `D:\GitHub\CAPTCHA`，2FA 使用已授权能力；只在真实认证场景调用，不把认证能力滥用到普通业务请求或无目标探测。
- **风险模式以提效为先**：默认采用 `managed`，非主力账号可直接采用 `aggressive`；主力账号也不因“可能风控”而阻塞自动化，仅在明确高危信号出现后隔离。

## 2. 最终用户体验

```text
用户：在 CloakMulti 登录账号
              │
              ▼
系统自动：绑定出口 → 记录网络身份 → 同步到目标网关
              │
              ▼
系统自动：巡检节点 → 处理同区故障 → 刷新订阅 → 冷却坏号
              │
              ├─ 普通故障：自动恢复，不通知
              ├─ 可逆风险：自动隔离、重试、观察，不通知
              └─ 要紧事件：暂停相关账号并微信通知

微信通知示例：
“需要处理：账号 A 触发 Google 验证，已暂停请求；请在 CloakMulti 完成验证。完成后回复：恢复 A。”
```

### 2.1 不通知用户的事件

- 单个节点短暂超时，且存在同国/同大区候选；
- 单次 408、网络断开、临时 5xx；
- 订阅刷新成功；
- 普通账号冷却和自动恢复；
- Flow 点数刷新、后台保活、健康检查成功；
- 账号在观察窗口内恢复正常；
- 自动任务的成功结果和常规日志。

### 2.2 必须微信通知的事件

- CAPTCHA、2FA、手机号验证或用户必须打开浏览器处理的页面；
- 账号主体与资料不一致；
- 跨国/跨大区出口漂移，且系统无法找到安全候选；
- 连续失败达到熔断阈值，自动恢复失败；
- 机场订阅失效、欠费、全部节点不可用；
- 凭据过期且无法通过受支持流程刷新；
- 账本冲突、数据文件损坏、原子写入失败或备份回读失败；
- 自动化组件自身失活：AgentProxyHub、Flow-Tools、Antigravity 或手机告警桥连续探活失败；
- 任何需要用户批准的跨服务商、跨区域或账号迁移动作。

## 3. 统一架构

### 3.1 职责边界

| 组件 | 自动化职责 | 不负责 |
|---|---|---|
| AgentProxyHub | 节点测绘、订阅刷新、端口池、网络身份、健康巡检、候选选择、租约和隔离 | 不保存 Google 凭据，不读取 Cookie，不替其他项目写私有账号库 |
| CloakMulti | 指纹环境、账号登录、2FA/CAPTCHA 人工协作、Profile 状态、登录完成事件 | 不直接写 Flow/Antigravity 私有数据库 |
| Flow-Tools | Labs 会话同步、点数、媒体任务、账号冷却、生成前网络检查 | 不自行跨区迁移账号，不接收未经约束的全量凭据 |
| Antigravity-Manager | OAuth 账号、LLM 会话粘性、模型调度、错误分类和自动重试 | 不读取 Flow 的 SessionToken，不由外部直接改 `user_tokens.db` |
| GLM-4flash | 结构化风险解释、候选排序、迁移建议、告警摘要 | 不直接执行换绑，不持有凭据，不绕过审批闸门 |
| 手机分身/微信 | 重要告警、用户指令回执、恢复结果通知 | 不作为第一控制面，不默认执行微信内存注入或自动温号 |
| Orchestrator | 事件编排、租约、状态机、重试、补偿、通知策略 | 不复制各项目私有数据，不成为新的事实账本 |

### 3.2 数据源分层

- **网络事实源**：AgentProxyHub 的节点测绘、真实探活、置信度和 `profile → port` 绑定。
- **浏览器事实源**：CloakMulti Profile 与实际登录状态。
- **媒体事实源**：Flow-Tools 账号池、Session 状态、点数和任务日志。
- **LLM 事实源**：Antigravity 自己的账号文件、会话粘性和路由日志。
- **决策记录**：GLM-4flash 输出和 Orchestrator 执行审计。
- **通知记录**：告警事件，不保存 Token、Cookie、Refresh Token 或完整请求正文。

## 4. 自动化策略：从保守模式切换为托管模式

### 4.1 三种账号策略

每个 Profile/账号登记一个自动化等级。为了提效，默认不再要求长时间观察后才能进入托管：新账号完成最小验证后直接进入 `managed`；用户明确愿意承担风险的账号直接进入 `aggressive`。

| 等级 | 用途 | 自动换线 | 自动恢复 | 微信策略 |
|---|---|---:|---:|---|
| `observe` | 仅用于调试或明确要求保护的账号 | 同一端口重试 | 仅冷却 | 要紧事件通知 |
| `managed` | 默认生产账号 | 同区优先，必要时跨服务商 | 允许认证辅助和有限换线 | 只报阻断事件 |
| `aggressive` | 用户明确授权的效率账号 | 允许跨服务商和有限跨区恢复 | 允许自动认证、换票、回切和任务迁移 | 只报预算耗尽或人工介入 |

默认策略：

- 新账号通过一次最小登录与出口校验后直接进入 `managed`；
- 非主力账号可默认进入 `aggressive`；
- 主力账号不因谨慎而阻塞自动化，只在明确的 CAPTCHA/2FA 连续失败、主体不一致或预算耗尽时隔离；
- `observe` 只作为故障排查模式，不作为所有账号的默认门槛。

### 4.2 自动换线边界

> 修订边界：效率授权针对已有合法访问权限的服务与本人管理的账号，不包含绕过服务地域限制、账号禁用、访问控制或平台明确要求的人工验证。跨区只能用于目标服务允许的网络恢复，不能作为地区限制的绕过手段。CAPTCHA 适配先等待本地技术文档核验，支持官方无障碍或服务认可的认证路径；用户授权本身不等于允许绕过反机器人安全措施。

在用户授权的托管模式下，系统可自动执行：

1. 当前节点连续探活失败；
2. 备用节点满足国家/大区约束；
3. 账号无正在进行的关键任务，或任务已进入可重试阶段；
4. 新节点真实 TCP、DNS 远端解析和目标站点探活通过；
5. 记录旧出口、新出口、国家码、服务商、端口、原因和回滚点；
6. 切换后执行一次轻量健康验证，再恢复请求。

默认禁止：

- 在生成/换票关键阶段无保护地热切；
- 同时批量切换多个主力账号；
- 失败后无限换节点；
- 无真实出口验证就相信静态 `nodes.json`；
- 发生跨国/跨大区时继续静默重试。

`aggressive` 模式可以允许跨服务商切换，但仍不允许无限尝试；跨国家/大区默认仍先暂停并微信通知，除非用户后续单独确认该账号的跨区策略。

## 5. 状态机

### 5.1 Profile/账号生命周期

```text
created
  → logged_in
  → network_verified
  → staged
  → validated
  → active
  → cooling
  → quarantined
  → user_action_required
  → active / disabled
```

约束：

- 收到登录资料不等于 `active`；必须完成出口、主体、凭据有效性和目标网关验证。
- `cooling` 可自动恢复；`quarantined` 默认停止请求，不做无界重试。
- `user_action_required` 必须微信通知，并保留现场。
- 状态转换必须幂等，重复事件不能重复换票、重复绑定或重复发送告警。

### 5.2 任务失败分类

统一归类为：

- `NETWORK_DOWN`：节点或本地服务不可用，可自动重试和换同区节点；
- `RATE_LIMIT`：指数退避并冷却账号；
- `AUTH_INVALID`：暂停账号，尝试受支持刷新一次，失败后通知；
- `REGION_BLOCKED`：停止当前账号重试，候选评估或通知；
- `CAPTCHA_REQUIRED`：立即隔离并微信通知；
- `主体不一致`：禁止继续写入，微信通知；
- `INVALID_INPUT`：直接返回，不自动重试；
- `DATA_CORRUPTION`：停止写入，使用备份/回滚流程并微信通知。

## 6. 分阶段落地计划

### Phase 0：自动化地基与运行基线

目标：让系统可以自我判断“现在到底运行了什么”。

任务：

1. 固化真实进程登记：PID、exe 路径、SHA、监听端口、Git SHA、数据目录、启动入口；
2. 统一 AgentProxyHub 生产账本路径，消除源码 `data` 与运行副本 `data` 分裂；
3. 保留端口段 `21001-21080`、`22001-22045` 不变；
4. 给所有跨项目事件加入 `event_id`、`dedupe_key`、`binding_revision`；
5. 建立统一健康状态采集器；
6. 建立每日摘要，但默认只写日志，不发微信。

验收：系统能自动生成一份状态快照，并且每个服务的健康结果与实际 PID/路径一致。

### Phase 1：AgentProxyHub 全自动网络维护

目标：用户不再手工维护网络。

任务：

1. 订阅刷新器：按节点存活率、快照年龄和机场状态触发；
2. 刷新前保存配置、节点快照、端口映射和 revision；
3. 先 dry-run 生成差异，确认端口段和绑定端口不变，再应用；
4. mihomo 热重载失败时回退上一份配置；
5. 按 Profile/账号策略执行同区候选切换；
6. 连续失败达到阈值后进入隔离，而不是无限重试；
7. 只有机场整体不可用、跨区风险或回滚失败才微信通知。

验收：模拟单节点失效、批量失效、订阅更新和热重载失败，系统能自动恢复或安全回退。

### Phase 2：CloakMulti 登录后自动纳管

目标：用户只负责登录，不负责复制资料和手工绑定。

任务：

1. 用户登录完成后，CloakMulti 发布“登录完成”事件；
2. Orchestrator 读取 Profile 标识和已绑定端口，不读取密码或2FA；
3. 触发 Flow-Tools 受支持的 `sync-profile`；
4. 自动处理资料关闭、锁释放、同步、点数刷新和账号状态回读；
5. Flow 验证通过后，按配置决定是否进入 Antigravity 的受支持导入流程；
6. 任一环节失败则保留 `staged` 状态，不伪装成 `healthy`；
7. 需要用户重新登录或验证码时，只发一条微信通知。

第一版不做：跨程序传递全量 Cookie、静默提取 OAuth Refresh Token、直接改写 Antigravity 私有数据库。

验收：使用一个非主力测试账号重复完成登录、同步、点数读取、最小真实业务请求和失败回滚。

### Phase 3：Flow-Tools 媒体号池托管

目标：普通生图/视频请求无需用户维护号池。

任务：

1. 账号按优先级、点数、冷却状态和网络身份调度；
2. 识别 401、地区限制、异常活动和高流量，不让坏号循环占用；
3. 失败账号进入冷却或隔离；
4. 正常节点故障自动选择授权范围内候选；
5. 输出产物、TaskLog、扣点和路由证据；
6. 只有全池不可用、验证码或账号需重新登录才微信通知。

验收：健康号、冷却号、过期号、地区限制和网络故障分别验证；真实请求必须回读官方产物链接和本地落盘结果。

### Phase 4：Antigravity 无人值守调度

目标：普通对话请求自动轮询和恢复，用户不参与网络维护。

任务：

1. 修复地区 400 导致的黏性会话死循环；
2. 仅对可安全降级的上游端点执行 fallback；
3. 对受影响会话清理粘性，不把所有 400 当成可重试；
4. 账号代理绑定由 Antigravity 自己的管理入口维护；
5. 自动轮换仅使用已有授权的账号与代理候选；
6. 网关失活、凭据失效、连续失败和需要重新授权时微信通知。

验收：`/health`、真实对话、路由日志、会话粘性、地区 400、429、401 和重启恢复全部闭环。

### Phase 5：GLM-4flash 决策增强

目标：让 Agent 能够替用户做日常判断。

任务：

1. GLM 只使用锁定的 `glm-4-flash`；
2. 输入 AgentProxyHub 审计、服务状态和错误分类；
3. 输出结构化动作：`retry`、`cooldown`、`switch_same_region`、`quarantine`、`notify_user`；
4. 对高风险动作增加策略检查；
5. 记录输入快照、模型、输出、执行结果和回滚点；
6. GLM 不直接接触任何账号秘密。

验收：同一输入产生幂等决策；危险动作被策略层拦截；普通维护不触发微信。

### Phase 6：微信重要事件闭环

目标：微信成为“异常处理台”，而不是日常日志窗口。

消息等级：

- `INFO`：不发微信，仅本地日志；
- `NOTICE`：聚合后日报或摘要；
- `ACTION_REQUIRED`：立即通知，等待用户指令；
- `CRITICAL`：立即通知并暂停相关账号/服务。

推荐指令：

- `状态`：返回服务、节点池、账号池摘要；
- `详情 <账号>`：返回脱敏故障现场；
- `恢复 <账号>`：解除人工隔离并启动有限恢复流程；
- `暂停 <账号>`：立即停止该账号任务；
- `批准切换 <账号> <候选>`：执行一次明确迁移；
- `全部静默` / `恢复通知`：调整通知级别，不改变安全闸门。

消息绝不包含 Cookie、Access Token、Refresh Token、完整代理密钥或完整请求正文。

## 7. 自动化优先级与不打扰策略

所有自动动作按以下顺序执行：

1. 读取当前状态；
2. 选择最小影响的恢复动作；
3. 设置幂等键和超时；
4. 执行动作；
5. 回读真实结果；
6. 失败则换更保守路径；
7. 连续同类失败达到阈值后停止并微信通知。

默认阈值建议：

- 单动作超时：30–90 秒，按服务类型配置；
- 同一账号同类错误：10 分钟内最多 3 次；
- 同一节点连续失败：3 次后隔离；
- 自动换线：每个账号每 30 分钟最多 1 次；
- 跨服务商切换：每个账号每 6 小时最多 1 次；
- 重要告警：同一 `dedupe_key` 10 分钟内只发一次；
- 无法验证出口身份：立即停止，不回退直连。

这些阈值是初始配置，先以日志观察 24–72 小时，再按真实失败率调整。

## 8. 回滚与故障处理

### 自动回滚

- mihomo 新配置加载失败：恢复上一份配置并重新探活；
- 绑定写入失败：保留原文件，删除临时文件，不以空对象覆盖；
- Flow/Antigravity 新版本探活失败：切回上一个已验证二进制；
- 账号导入部分成功：保留 `pending`，不删除原账号；
- 自动换线后业务验证失败：恢复旧租约；旧出口不可用时进入隔离并微信通知。

### 不自动回滚的情况

- 凭据疑似泄漏：吊销、轮换、隔离，不恢复旧密钥；
- Google 已明确要求验证码/2FA：暂停等待用户；
- 数据库格式不兼容：停止写入，保留现场，微信通知；
- 跨区迁移已发生且授权被撤销：不自动反复切换，等待人工判断。

## 10. CAPTCHA 与 2FA 授权适配

用户已明确授权：

- CAPTCHA 场景可调用 `D:\GitHub\CAPTCHA` 中的本地授权能力；后续以该项目写入的正式技术文档和接口契约为准。
- 2FA 场景可调用已授权的本地 2FA 能力。
- 两类能力只在对应认证场景触发，不得用于普通请求、批量探测、绕过非认证限制、伪造用户行为或无限重试。

### 10.1 触发条件

只有满足以下条件之一才允许调用认证辅助能力：

1. 目标页面或接口明确返回 CAPTCHA/挑战信号；
2. 登录流程明确进入 2FA/TOTP/一次性验证码步骤；
3. 当前任务属于用户已登记的账号/Profile，且认证上下文、出口和目标服务一致；
4. 本次调用拥有唯一 `request_id`、任务来源和超时预算。

普通 401、403、429、网络超时、地区限制或模型错误，不得直接当作 CAPTCHA/2FA 触发条件。

### 10.2 调用前后约束

- 调用前校验账号、Profile、目标域名、当前代理身份和授权范围；
- CAPTCHA 只向目标认证页面提交必要挑战数据，不把 Cookie、Access Token 或 Refresh Token 写入日志、截图、微信消息或仓库；
- 2FA 只在对应账号的真实登录流程中使用，不跨账号、不跨 Profile、不作为批量撞库或枚举工具；
- 每次调用必须有超时、次数上限、失败分类和幂等键；
- 连续失败、挑战类型不匹配、目标域名不在白名单或主体不一致时立即停止并微信通知；
- 成功后仍必须继续执行出口、主体、会话和业务健康校验，不能因 CAPTCHA/2FA 成功就直接标记账号 `active`；
- 后续 `D:\GitHub\CAPTCHA` 技术文档落地后，补齐接口版本、白名单、审计字段、数据保留期和撤销机制。

### 10.3 认证状态机

```text
auth_required
  → challenge_detected
  → captcha_or_2fa_authorized
  → credential_validated
  → business_health_verified
  → active

任何步骤失败 → user_action_required / quarantined
```

认证辅助成功只代表“挑战步骤完成”，不代表账号已经可用于 Flow、Antigravity 或其他业务。

## 11. 进一步优化建议

### 11.1 把 Orchestrator 做成唯一自动化控制面

AgentProxyHub、Flow-Tools、Antigravity 和 CloakMulti 不互相猜状态。Orchestrator 只保存任务状态、租约、事件和执行记录，调用各项目现有接口完成动作，避免再产生第二套账号池或第二套代理账本。

### 11.2 引入策略配置而不是散落硬编码

将以下内容集中配置并支持按账号/Profile 覆盖：

- 自动化等级；
- 国家/大区约束；
- 是否允许跨服务商；
- 自动换线冷却时间；
- 最大重试次数；
- CAPTCHA/2FA 是否可调用；
- 微信通知等级；
- 允许自动恢复的错误类型。

策略修改必须版本化、可回滚，并在每次自动动作中记录命中的策略版本。

### 11.3 把“网络身份”升级为租约

绑定不只记录端口，还记录 `binding_revision`、账号/Profile、provider、国家码、实测 IP、租约开始时间、TTL、最近验证时间和风险状态。租约过期时先续租或隔离，不直接把端口交给其他账号，避免旧任务和新账号串线。

### 11.4 增加自动化预算与熔断器

为每个账号、节点、服务和全局设置独立预算：

- 每小时最大换线次数；
- 每小时最大认证辅助次数；
- 每次任务最大重试次数；
- 全局并发认证任务数；
- 单日微信告警上限；
- 单一节点的最大失败占比。

预算耗尽后进入隔离或通知，不继续扩大损失。

### 11.5 建立“影子模式”再开启自动执行

新策略先只记录“如果执行会做什么”，不真正换线、不写绑定、不调用认证辅助。连续观察 24–72 小时，确认误判率、告警量和候选质量后，再按账号等级逐步开启。

### 11.6 做事件溯源而不是只写普通日志

每个自动动作记录：`event_id`、触发事件、策略版本、输入快照摘要、候选方案、实际动作、结果、耗时、回滚点和通知结果。敏感字段只记录哈希或脱敏标识，保证可以解释“系统为什么这么做”。

### 11.7 将微信控制设计为有限状态操作

微信指令不直接执行任意脚本，只能调用预登记动作：状态、暂停、恢复、批准一次切换、重新认证。高风险指令使用一次性确认码和短时有效期，避免误触或重复执行。

### 11.8 认证与网络身份绑定

CAPTCHA/2FA 成功后，必须绑定本次认证的 Profile、出口国家码、provider、任务和时间窗口。认证过程中出口身份发生变化时，立即废弃本次认证结果并重新进入验证，避免把一个出口签发的会话带到另一个身份上。

### 11.9 增加“安全降级路径”

自动化失败时按以下顺序降级：

1. 重试当前出口；
2. 同国家/大区候选；
3. 账号冷却并切换其他已授权账号；
4. 暂停相关账号并微信通知；
5. 保留现场等待人工处理。

不得从自动化失败直接降级为裸直连，也不得跳过认证状态机。

## 12. 完成定义

计划不能以“代码写完”作为完成。每一阶段必须同时满足：

1. 静态检查通过；
2. 候选与正式运行副本隔离；
3. 不覆盖用户账号数据；
4. 服务健康探针通过；
5. 至少一个真实、低成本、可回读的端到端用例通过；
6. 故障注入或模拟回滚通过；
7. 普通事件不打扰用户；
8. 要紧事件微信可达、去重、可执行；
9. 保留上一可运行版本和数据恢复点；
10. 计划中的“已实现”与“待实现”状态同步回维护文档。

## 11. 手机分身与 AgentProxyHub 联动方案

### 11.1 结论

**需要联动，但不建议把手机分身直接接入 AgentProxyHub 的代理数据面。**

手机分身的最佳定位是“独立的通知与人工介入终端”，而不是代理节点、账号账本或恢复逻辑的参与者：

```text
AgentProxyHub / Flow / Antigravity / CloakMulti
                    │
                    ▼
              本机事件总线
        （事件、状态、命令、回执）
                    │
                    ▼
              手机分身适配器
                    │
                    ▼
                 微信通知
```

手机分身只接收脱敏事件、发送有限指令、返回处理回执；不读取 `bindings.json`、Cookie、OAuth、代理订阅或账号数据库。

### 11.2 为什么不让手机分身直接吃 AgentProxyHub 代理

1. **职责更干净**：AgentProxyHub 负责网络身份，手机分身负责通知和人工入口。
2. **故障隔离**：手机断开、微信异常不会影响代理池和生成任务。
3. **安全面更小**：手机端不接触代理密钥、订阅链接、账号凭据。
4. **体验更优雅**：AgentProxyHub 只向事件总线投递重要事件，不需要知道微信页面、ADB 或手机 UI 细节。
5. **未来可替换**：微信、邮件、桌面通知或其他终端都可以复用同一事件，不改 Hub 核心。

### 11.3 已有链路的优雅化

已知本机已有 `48921` 通知链路和 ADB 通道。建议将其收敛为一个小型 `AlertBridge`，而不是让各项目分别调用手机：

- Hub、Flow、Antigravity、CloakMulti 只投递统一事件；
- `AlertBridge` 负责去重、合并、优先级、发送、重试和回执；
- 手机分身只负责接收通知和返回有限命令；
- ADB/USB 断开时事件落盘，恢复后自动补发；
- 不把“端口监听”当作消息送达，必须记录 `queued/sent/ack/expired` 状态。

统一事件字段：

```json
{
  "event_id": "evt_...",
  "dedupe_key": "account-a:captcha-required",
  "severity": "notice|action_required|critical",
  "component": "agentproxyhub|flow|antigravity|cloakmulti",
  "profile_id": "脱敏标识",
  "action": "resume|pause|reauth|approve_switch|none",
  "summary": "脱敏白话摘要",
  "expires_at": "2026-09-30T18:00:00Z"
}
```

禁止事件包含 Cookie、Access Token、Refresh Token、完整代理密钥、订阅 URL、完整邮箱或原始请求正文。

### 11.4 微信只做“异常处理台”

手机端默认静默处理以下事件：

- 节点切换成功；
- 订阅刷新成功；
- 单号冷却和自动恢复；
- 普通网络重试；
- Flow 点数刷新；
- 服务短暂重启。

只在以下事件通知：

- 全池不可用且自动恢复失败；
- CAPTCHA/2FA/新授权必须用户处理；
- 账号主体不一致；
- 数据损坏或凭据安全事件；
- 自动化预算耗尽；
- 需要批准一次高风险切换；
- AlertBridge 自身离线后恢复，需要报告期间遗漏事件。

### 11.5 微信指令采用短命、有限动作

手机分身可以联动 AgentProxyHub，但只能通过 AlertBridge 的白名单命令，不直接执行脚本：

- `状态`：返回脱敏服务摘要；
- `详情 <事件>`：返回事件上下文；
- `暂停 <对象>`：暂停账号或任务；
- `恢复 <对象>`：解除隔离并执行有限恢复；
- `重新认证 <对象>`：重新进入 Cloak/认证流程；
- `批准切换 <事件>`：只批准当前事件的一次迁移。

每条命令必须绑定 `event_id`、一次性确认码、过期时间和执行回执。重复命令返回原回执，不重复执行。

### 11.6 什么时候才让手机分身使用 AgentProxyHub 代理

只有手机分身自身需要访问外部服务时，才给它分配独立 Profile/端口，例如：

- 手机端确实需要固定地区的外部 API；
- 手机端需要与特定账号保持固定网络身份；
- 手机端的业务流量必须经过指定出口审计。

这时它作为普通消费者向 AgentProxyHub 申请独立绑定，使用独立端口和独立账本项；**不复用 Google 账号端口，不使用 AUTO-POOL，不读取其他账号的绑定**。单纯的 ADB/USB 本地通知链路不需要经过 AgentProxyHub。

### 11.7 手机联动验收

1. Hub 产生高优先级事件，AlertBridge 入队；
2. 48921/ADB 链路送达手机；
3. 微信消息只含脱敏摘要；
4. 用户回复一次性命令；
5. Hub 执行一次白名单动作；
6. 回执回到微信；
7. 重复消息不重复执行；
8. USB 断开时事件不丢，恢复后补发；
9. AlertBridge 停止时业务系统仍能继续运行；
10. 手机分身不持有代理密钥、订阅凭据或业务账号秘密。

## 12. 第一批实际执行顺序

1. 先完成运行基线和 AgentProxyHub 生产账本路径收敛；
2. 实现网络自动维护的 dry-run、差异、热重载回滚和重要告警；
3. 用一个非主力测试 Profile 打通登录完成 → Flow sync-profile → 点数 → 最小业务请求；

6. 接入 GLM-4flash 只读决策建议；
7. 最后把批准、恢复、暂停等微信指令接入受控执行器；
8. 连续观察 24–72 小时后，再扩大到更多账号。

## 12. 明确承诺

- 用户不需要参与普通网络维护；
- 系统优先自动处理可逆故障；
- 系统不因小故障频繁打扰微信；
- 关键事件一定保留现场并通知；
- 任何自动动作都有超时、次数上限、审计和回滚路径；
